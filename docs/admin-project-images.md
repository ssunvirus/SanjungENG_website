# 관리자 시공사례 사진 업로드

기존 public 사진은 유지하고 새 사진만 S3에 저장합니다.
관리자 사진 조회 API는 인증을 요구합니다. DB 저장 사례에서 참조하는 사진은 별도의 공개 API로 홈페이지에 표시합니다. [홈페이지 연결 안내](./public-projects.md)를 참고하세요.

## 1. S3 버킷 생성

AWS S3 → 버킷 만들기:

- 리전: 아시아 태평양(시드니), ap-southeast-2
- 유형: 범용
- 이름 예: sanjung-project-images-235390156511 (사용 가능한 이름으로 지정)
- 객체 소유권: ACL 비활성화, 버킷 소유자 적용
- 모든 퍼블릭 액세스 차단: 켜짐 유지
- 버전 관리: 초기에는 비활성화
- 기본 암호화: SSE-S3

브라우저는 같은 사이트의 서버 API로 업로드하므로 S3 CORS와 퍼블릭 버킷 정책은 필요하지 않습니다.
이미지 이름은 무작위 UUID로 생성하며 원래 파일명은 저장하지 않습니다.

## 2. 컴퓨팅 역할 권한

IAM → 역할 → SanjungAmplifyComputeRole → 인라인 정책 추가.
이름 예: SanjungProjectImagesReadWrite. 아래 버킷 이름을 실제 생성한 이름으로 바꿉니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::sanjung-project-images-235390156511/projects/*"
    }
  ]
}
```

기존 DynamoDB·Cognito·메일 권한은 유지합니다. AWS 액세스 키를 별도로 만들 필요는 없습니다.

## 3. Amplify 환경변수 및 배포

호스팅 환경변수 `PROJECTS_IMAGES_BUCKET`에 실제 버킷 이름을 입력합니다.
기존 `PROJECTS_AWS_REGION=ap-southeast-2`를 함께 사용합니다.
코드를 배포한 뒤 관리자에서 사진 선택 → 설명 입력 → DB에 저장 → 새로고침으로 확인합니다.

## 동작과 제한

- JPG·PNG·WEBP만 지원, 사진당 3MiB, 사례당 최대 30장.
- 서버 업로드 경로의 요청 크기를 제한하기 위해 한 장씩 순차 전송합니다.
- 인증·동일 출처·MIME·파일 시그니처·크기를 서버에서 검사합니다. 시그니처 검사는 완전한 이미지 디코딩 검사가 아닙니다.
- 사진 업로드와 DB 저장은 별개입니다. 업로드 후 DB 저장 버튼을 눌러야 사례에 연결됩니다.
- 부분 실패 시 성공한 사진은 화면에 남깁니다. 해당 사진을 DB에 저장한 후 실패한 사진만 다시 선택합니다.
- 사진 목록에서 제거 후 저장하면 DB 연결이 해제됩니다. 미사용 S3 파일은 아래 정리 기능으로 삭제할 수 있습니다.
- 저장하지 않고 나간 업로드나 통신 중단으로 생성된 미연결 파일도 S3 목록에서 찾아 정리합니다.
- 기존 public 사진을 S3로 일괄 이동하거나 기존 홈페이지 데이터를 변경하지 않습니다.

[AWS S3 PutObject 문서](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/client/s3/command/PutObjectCommand/)

## 미사용 사진 정리

관리자 시공사례 목록에서 **미사용 사진 확인**을 누릅니다.
S3의 `projects/` 목록과 DB의 모든 사례 사진을 비교하며, 업로드 후 24시간 이상 지난 미사용 사진을 오래된 순서로 최대 20장 미리 보여줍니다.
확인 후 **위 사진 완전 삭제**를 누르면 해당 파일을 삭제합니다. 20장이 넘으면 조회·정리를 반복합니다.
자동 예약 작업은 없으며 버튼을 눌렀을 때만 정리합니다. 별도 추적 DB 항목 대신 S3 객체의 키·수정 시간·크기를 사용하므로 이전에 남은 파일과 재시작 후 실패한 삭제도 다시 찾을 수 있습니다.

- DB에서 사용하는 사진과 사례 삭제 재시도 대기 중인 사진은 제외합니다.
- 삭제 요청 때 파일 나이와 DB 연결을 다시 검사하며, 개별 삭제 직전에도 DB를 재조회합니다.
- DB/S3 조회가 실패하면 삭제를 중단합니다. 삭제에 실패한 객체는 다음 조회에 다시 나옵니다.
- 기존 `public` 파일과 UUID 사진 규칙에 맞지 않는 객체는 건드리지 않습니다.
- 다른 창이나 다른 관리자가 편집 중이면 먼저 저장하고 정리하세요. 여러 저장과 S3 삭제를 하나의 트랜잭션으로 잠그는 구조는 아니므로 정리와 사진 재연결을 동시에 진행하지 않습니다.
- 24시간은 업로드 시각 기준입니다. 24시간 넘게 저장하지 않은 편집 내용은 보호하지 못하므로 먼저 저장해야 합니다.
- 버전 관리가 비활성화된 버킷을 전제로 합니다. 버전 관리가 켜져 있으면 삭제 마커만 생겨 이전 버전 저장 비용이 남으므로 별도 버전 정리가 필요합니다.

`SanjungAmplifyComputeRole`에 다음 정책을 추가합니다. 기존 업로드·조회 권한은 유지합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::sanjung-project-images-235390156511",
      "Condition": { "StringEquals": { "s3:prefix": "projects/" } }
    },
    {
      "Effect": "Allow",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::sanjung-project-images-235390156511/projects/*"
    }
  ]
}
```

DB의 `Scan` 권한과 사진 미리보기용 S3 `GetObject`는 기존 권한을 사용합니다.
배포 후 미사용 사진 조회 → 사진 확인 → 삭제 → 재조회로 사라졌는지 확인하고, 공개 중인 사례의 사진은 그대로 보이는지 확인합니다.
